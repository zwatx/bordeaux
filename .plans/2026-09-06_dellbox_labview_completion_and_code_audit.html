Findings

1. P1 — False asynchronous conditions exponentially delay unrelated events

labview/native/runtime.cpp:517–520; related result consumption at 374–377 and one-shot retry at 535–536. The event loop returns on its first unresolved condition and restarts from the beginning on the next tick. Earlier false results have already been consumed, while those events remain due, so they are requested again before later results can be used.

Reproduced against the shipped Linux shared library with every callback answered immediately: five false conditions preceding a due unconditional command delay it to tick 32 (0.64 s at 20 ms); ten delay it to tick 1,024 (20.48 s). Inline condition snapshots dispatch it on tick 1. The Java loop at BordeauxEventRunner.java:109–122 continues through false conditions within the same periodic pass. This can suppress an otherwise valid autonomous action until the path has already ended.

Fix: preserve the pending evaluation pass/cursor and results, or use another bounded approach that avoids repeated evaluation while retaining ordering. Add callback-based multiple-false-condition regressions, including path-end/window expiry. The current differential tests supply inline snapshots and miss this path.

2. P2 — UTF-8 truncation prevents mailbox rejection and acknowledgment

labview/native/revision.cpp:831–837. rejection.substr(0, 512) can split a UTF-8 character. Serializing the acknowledgment then throws, before the acknowledgment is written and the input is removed at lines 840–842.

Independently reproduced using a temporary local mailbox and a correctly hashed revision whose invalid routine node type contains a long accented string. Two consecutive polls both return incomplete UTF-8 string; last byte: 0xC3; the request remains and no acknowledgment exists. Subsequent queue entries can remain blocked behind it. The Java bounded-message path handles this BMP text as characters.

Fix: truncate on complete UTF-8 characters while retaining the acknowledgment byte limit. Test a multibyte boundary and confirm the rejection is acknowledged/removed and the following request is processed.

3. P2 — Mixed project roots silently change an existing Java link to LabVIEW

src/electron/main.ts:304–305. Any root .lvproj makes connection/restoration select LabVIEW, even when an existing Gradle/Java project and bookmark are present. There is no retained runtime selection or ambiguity choice. A fixture with an existing Java command loses that catalog when a Robot.lvproj is added; the same root then selects an empty LabVIEW catalog and different installation/export paths.

Fix: preserve the selected runtime in the bookmark or explicitly resolve roots containing both project types. Cover restoration of existing Java links and choosing either runtime.

4. P2 — LabVIEW installation displays Java-only next steps

src/renderer/app/App.jsx:525. The newly shared installation callback always instructs users to annotate Java command factories and read .bordeaux/INTEGRATION.md for RobotContainer wiring. LabVIEW installation creates bordeaux/support and bordeaux-catalog.json, not that guide or Java bindings.

Fix: select the notice by the returned runtime and link to the installed LabVIEW setup/catalog workflow. Verify the immediate post-install state; the UI harness clears the notice during the next build and misses it.

5. P2 — The setup catalog example does not compile

docs/labview/setup.md:37 and its distributed copy under labview/artifacts/docs/labview/setup.md use "min":"-1","max":"1" for a numeric parameter. The catalog parser requires numbers and rejects the exact example with Generated Java catalog parameter minimum must be finite. Changing only those bounds to JSON numbers succeeds.

Fix: correct the example and regenerate the distributed documentation/manifest. Add a check that extracts and compiles the getting-started example.
