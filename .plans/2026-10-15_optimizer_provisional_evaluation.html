Original engineering contract — historical context

The sections below preserve the 2026-10-15 source contract that led to the experiments. They describe intended boundaries and acceptance gates, not a current claim that screening is unimplemented or approved for activation. Source pins are historical inspected inputs.

1. Existing boundaries to retain

corridorFinal.ts:261 currently prepares optimizeFixedGeometryFinal once, preserves its validated baseline, explores four handle-length patterns and up to three local passes, and performs a full getPlanner('optimizedTrajectory').generate for each geometry that passes the route-deviation check. The full planner includes initial reachability, dense validation/refinement/local retiming, coupled heading recovery, stationary actions and, when eligible, an additional double-density Normal comparison (optimizedTrajectory.ts:408, index.ts:149–293). This is the expensive work to avoid for unpromising trials.

The search baseline remains exactly optimizeFixedGeometryFinal(input) (fixedGeometryFinal.ts:238). It compares and validates the existing Normal and optimized-family fixed-route results. It is not interchangeable with the editor's authored Normal56. Preserve the new useOptimizerComparison contract, zero-duplicate open/reopen behavior, full Normal reference, artifact qualification and pending-only Apply bridge. Search statistics cannot populate its reference.

corridorFinal.ts:386–416 is the authoritative candidate boundary: full planner generation, fallback/error refusal, sampled physical validation, exact portal sequence, gates, footprint corridor and field clearance. Preserve all of those checks and their current resolutions/tolerances. acceptedTrajectory.ts remains an independent later check of intent, marker timing, stationary actions, geometry/heading invariants, dense validation and authored corridor. No accepted/export validator is removed, bypassed or given a provisional shortcut.

2. One private estimate, using existing primitives

Add src/shared/planners/corridorProvisional.ts with a narrow export used only by corridor search and its tests:

type CorridorEstimate =
  | { kind: 'ranked'; version: 1; density: number; estimatedTimeS: number }
  | { kind: 'unranked'; version: 1; density: number; reason: string };

function estimateCorridorCandidate(input: PlannerInput): CorridorEstimate;

It returns no samples, PlannerResult, optimization status, accepted flag or preview. estimatedTimeS is a heuristic score, not a feasible time or certified lower bound. No renderer/worker message carries it as a trajectory. Keep candidate geometry and estimate together in the search's local record; never reconstruct geometry from a score.

The first implementation uses the caller's base density, 56 in the production final worker. Do not also introduce lower sampling density in this increment. The intended savings come from omitting repeated dense/refinement/recovery/family-comparison work. Non-56 shared callers retain their own density; a score is never relabeled as density 56. Reject invalid density before work through the existing seed boundary. Any later lower-density estimator is a separately versioned, measured change.

Reuse the already exported functions; no new solver or general planner framework is needed:

  1. canonicalPlanningInput from index.ts:118 supplies the same legacy-priority removal, robot physical limits and wait-free moving solve as authoritative planning.
  2. profiledSplineOptimizationSeed(planningInput) supplies one full-precision geometry/heading seed. This is the raw seed API, not getPlanner('profiledSpline'), which invokes the strict solver. Do not derive the rounded fallback as well merely to estimate.
  3. insertOptimizationBoundaries, remapWaypointIndices, buildReachabilityInput, one solveReachabilityProfile and remapTiming supply one sample-aligned moving estimate. Keep all authored constraint/target/stop knots and exact endpoint velocities. Do not substitute distance divided by max speed or discard heading constraints.
  4. Apply the existing applyRotationPriority and applyStationaryActions once, using the physical authored path and robot. That keeps stops, fractional waits, explicit/implicit turns and heading/reverse conventions represented in the estimated duration. No refinement, dense-validation or recovery loop runs here. Jiggle still takes the existing unsupported-search baseline path before estimation.
  5. Check finite, positive duration and structural/sample sanity, then run the existing sampled physical check at this density. Missing samples, unsuccessful reachability, diagnostic errors, sampled violations or computation exceptions return unranked, not a declaration that the final candidate is impossible. The full planner may repair a rough failure.

The helpers accept PlannerResult internally. A local intermediate may therefore use that structural shape, but it must not carry fabricated optimal/feasible, zero-violation or dense-validation claims, and it never escapes this module. For a duration-only intermediate, marker metadata need not be produced: use an empty intermediate marker list without altering input.path.markers. Markers do not add motion duration. All marker fractions/times/invocations/order in an actual candidate are freshly produced by the full finalizer. Do not expose stale seed marker times as if they followed the provisional retime.

There is no proof this estimator is cheap enough yet. PM.derivePath and action/heading expansion still do real work. If sampled failures force most candidates through the full planner, the result can be slower. Measure that outcome rather than removing physical/action semantics to improve the number.

3. Search policy: one candidate at a time

Use an online screening gate within the existing evaluate(path) seam. Keep handle variables, four pattern order, local factor order, maximum evaluations, three-pass limit, and strict-result-driven local movement. Do not use an unvalidated path as the local-search center. A bounded batch shortlist is unnecessary for the first increment and would complicate prefix behavior and end-of-budget finalization.

Prepare a reference estimate of the authored geometry after publishing the valid strict baseline, only when the cancellation and reservation gate in §5 admits that reference work. If the baseline already exhausted the budget, publish it and perform zero estimate calls. Retain an estimate only for the geometry of the current validated best. Compare a trial's score against that same estimator's score for best.path, never against its authoritative duration or candidate search-baseline statistic.

For each candidate admitted by the existing work/cancel gate:

  1. Increment the existing geometry-evaluation ordinal and run the unchanged high-resolution authored route-deviation check (max(128, baseDensity * 2)). A rejection here remains a real corridor rejection and needs no estimate.
  2. If the current best estimate is unavailable, bypass screening and use the current full evaluation path. Do not pay repeated estimation work without a usable reference. A new fully validated best may receive one budget-admitted reference estimate after its completed strict checkpoint is published, as described below.
  3. Otherwise compute the trial estimate. Fully finalize when the estimate is unranked, when it beats the best-geometry estimate by the existing numerical epsilon, or when the evaluation ordinal is a fixed exploration slot. Proposed initial exploration schedule: every fourth geometry evaluation, independent of requested total work or elapsed time. This guards against permanently trusting a biased ranking; four is an experimental policy constant, to be accepted or revised only against the pinned quality/cost gates below, not represented as a measured optimum.
  4. A nonpromising ranked trial outside an exploration slot is screened from further work. Record this explicitly; it did not fail physical validation.
  5. Recheck cancellation and available finalization budget. If admitted, call the unchanged authoritative candidate path at the original caller density. No reuse of provisional samples or feasible-status fields. Update best, local-search state, and the geometry-associated estimate only from a fully validated actual result whose actual time is smaller. Preserve the current baseline-relative material publication threshold: at least max(0.02 s, 0.005 * baselineTimeS).

When a new strict best already has a trial estimate, retain that exact ranked or unranked result for its geometry; do not recompute it. Otherwise settle the trial counters and publish any completed material strict improvement before optional reference refresh. On cancellation or insufficient remaining budget, skip refresh and stop or leave ranking unavailable while preserving the published checkpoint.

This policy has no pending shortlist, no asynchronous per-candidate work and at most one additional estimate/intermediate in memory. Authoritative calls are at most one per admitted geometry and remain bounded by the unchanged 24/48/72 defaults and maximum 72. It does not guarantee fewer full calls on every input; fallback to the existing full path is intentional when ranking is unavailable.

Keep the schedule independent of maximumEvaluations so fixed-clock runs with more work preserve the same decision prefix, including ordinal-based exploration. Do not scale the screening threshold or finalist quota according to the requested ceiling. Existing fixed-ceiling deterministic and increasing-work/non-worsening tests remain meaningful with their current ceilings and assertions. No provisional best or end-of-budget queue flush may change an earlier prefix decision.

4. Authoritative finalist and safety gates

Extract the current full candidate body into a small local function only if that makes the boundary clearer. It still takes the exact candidate PathDoc and current PlannerInput and returns the current Evaluation | null; it is not a second approximation API.

  • Production finalization starts at 56. The current planner may refine or select its 2× Normal result; preserve its actual refinementPasses/samples and the artifact's base-density meaning. “Authoritative56” does not mean force every result to exactly 56 intervals.
  • Re-run the existing full planner and sampled validator; retain full-planner dense validation, coupled recovery, stationary action handling and failure refusal. Preserve all positive limits/tolerances, robot forces, endpoint poses/velocities, heading/targets, stop/wait/turn intent and marker semantics.
  • Use the unchanged high-resolution route check, full trajectory portal sequence, ordered gates, swept footprint and minimum field clearance. No coarse approximate portal/footprint/gate success can authorize a finalist. An early exact route rejection is safe; a rough heading/topology failure is only an unavailable ranking and must not masquerade as a full validation failure.
  • Keep validateCorridorCandidate, invariantFailure, validateFinal, getAcceptedTrajectory, createAcceptedTrajectory and strict export selection unchanged. Regression tests independently feed every published/final result through the accepted/export boundary. Do not add the whole expensive accepted validator to every cheap trial or replace the existing finalizer with it merely to simplify the implementation.
  • Current unsupported conditions remain: ambiguous authored portal topology, non-Bézier paths, segment limit, no movable handles and jiggle retain the strict baseline with existing status. Failed baseline produces existing invalid-input evidence and no valid checkpoint.

Candidate identity is local to the unique search job plus exact immutable candidate geometry, robot/field, base density, estimate version and resolved search options (corridor, clearance, gates, tier, time/work ceiling). Keep an ordinal/record association; a new per-render hash or global score cache is unnecessary. The existing physical key excludes density and search options, so it alone cannot identify an estimate. Accepted artifact version/physical-key version need not change because strict result semantics remain unchanged; record a separate search-strategy version in optimization diagnostics for benchmark interpretation.

5. Budget and checkpoint rules

There are three distinct bounds: total candidate work, cooperative search time, and the existing external FinalPlanning worker deadline (tier budget plus 1,000 ms grace). Keep 5/15/30-second tiers and the external grace unchanged. A synchronous physics solve is not interruptible; no conservative estimate is a hard completion guarantee.

Publish the initial strict baseline at the earliest existing safe point, before baseline scoring or candidate screening. This means immediately after strict baseline validation/eligibility, not a promise that the baseline itself is instantaneous or survives a hard timeout before it completes. Invalid baseline cannot produce an incumbent.

Track elapsed maxima separately for provisional work, authoritative finalization and synchronous checkpoint callback/projection. Every estimator call, including initial and refreshed reference estimates, is cancellation- and budget-admitted and contributes to the provisional elapsed maximum. Before a reference estimate or provisional trial, reserve time for a possible full finalist and publishing; before starting the full finalist, check the reservation again. An implementable initial conservative reservation is:

publishReserve = max(100 ms, 1.25 * longestPublishCallbackMs)
finalReserve   = 1.25 * max(strictBaselineElapsedMs, longestFinalistMs)
trialReserve   = 1.25 * longestProvisionalMs
start any estimate only if remaining > publishReserve + finalReserve + trialReserve
start finalist only if remaining > publishReserve + finalReserve

Initial/reference estimate attempts do not consume a geometry-trial ordinal or enter the public trial partition. Retain their counts and elapsed cost separately in measurement evidence; this includes all optional refresh attempts. A reference estimate is never allowed ahead of publishing a completed strict improvement.

The strict baseline's measured cost initializes the finalizer estimate; it is not claimed to bound it. This can be too conservative on a slow baseline and produce no search work. Treat that as a measurable quality/latency failure to tune before activation, not permission to consume all time scoring or increase the hard deadline. Keep reservation constants private, deterministic with a controlled clock, and distinct from physical limits. With the existing fixed zero work clock, time reservations must not cut off deterministic work-ceiling tests.

Check isCancelled before each stage and before committing a newly finalized result. Cancellation retains the last already-published strict checkpoint, never the most promising score. If an indivisible full solve finishes after the cooperative budget but before external termination and is not canceled, it may publish its fully validated improvement and then stop; do not discard safe completed work solely because the cooperative clock elapsed during it. The external worker can still terminate at any point and retain only its last received strict preview.

onProgress publishes only baseline/materially improved validated incumbents. onStatistics carries counters only. A failed finalist cannot overwrite retained samples/route/status. Keep corridor callbacks outside computational rejection catches. Exceptions from the worker-side projection/progress/statistics boundary propagate through the worker error response and settle the request as failure rather than being swallowed and counted as rejected physics. FinalPlanning retains earlier validated incumbent metadata on timeout/cancel/error and rejects stale request IDs as it does today. A separate renderer-side requestConfig.onProgress throw currently occurs outside the controller failure handler; this contract does not claim that unrelated callback immediately settles as failure or silently broaden the increment to fix it.

6. Honest counters and transport

Keep evaluations as admitted geometry trials, including exact route rejections and screened trials. Therefore a larger number no longer means more full validations. Do not compare this number alone against the previous algorithm to claim doubled throughput.

Keep the existing settled accounting identity evaluations = validatedCandidates + rejectedCandidates, with rejectedCandidates explicitly meaning not admitted as a validated candidate, rather than exclusively physically infeasible. Use truthful reasons for heuristic and budget decisions. Add only the counters needed to distinguish the work:

FieldMeaning

finalizedCandidatesAuthoritative candidate calls actually attempted, including computation/validation failures. Excludes strict baseline.
screenedCandidatesSubset of rejected candidates skipped solely by the provisional ranking policy.
Existing validatedCandidatesCandidates passing all authoritative and corridor gates, whether or not they improve the incumbent.
Existing rejectedCandidates / reasonsExact route/full-finalizer rejection, heuristic screening, or a trial abandoned before finalization for budget/cancel; reasons distinguish these.

Examples: Screened by provisional estimate, Final validation not started: search budget exhausted, and the existing concrete physical failure. The bounded overflow reason should be neutral (Other candidate rejections), not falsely describe every screen as a validation failure. An unranked estimate that is later validated counts as validated, not rejected. A fully validated but nonimproving trial remains validated. Record stage counters once, never again when a candidate is projected/published.

Publish statistics only at settled trial boundaries so the partition holds. If the worker dies inside a stage, the retained metadata describes the last completed reported checkpoint; it must not claim a half-finished estimate was validated. No new per-trial progress message containing samples is needed.

Extend PlannerOptimizationDiagnostics, CorridorSearchStatistics, the explicit STATISTICS_KEYS whitelist in final-planning.js, and their focused transport tests together. Keep strategy-version metadata in the immutable incumbent diagnostic, not in the counters-only overwrite whitelist. Existing statistics must still be unable to replace samples, route, duration, feasibility or current selection. No UI redesign or new controls are part of this contract.

7. Current-document ownership prerequisite

The search's current request-ID/active === job/physical-key checks remain necessary. Source inspection also exposes an existing narrower gap: path-optimization.js:run matches path ID and physical key after cancellation, while App.loadProject cancels the optimizer then replaces the project. A canceled old job can return its incumbent for a new document with the same ID/key; completed store entries likewise have no document generation. This is a source-derived race scenario, not a reproduced native finding or a defect introduced by provisional evaluation.

Before adding new search work, cover that scenario with a deferred public-owner test and bind search entries/jobs to the existing App document epoch:

  • Supply a stable getDocumentKey: () => documentEpoch.current to PathOptimization.create; capture it in each job and stored entry. Do not use project object identity, which changes on every edit.
  • Refuse completion if its document key is no longer current even when path/key match. sync() detects a document-key change, cancels old work, invalidates batch continuation and drops old entries.
  • App's candidate selection checks the entry's document key during render, before an effect can clear the store. This prevents a same-ID/key old entry from briefly becoming an applicable candidate.
  • Explicit user cancellation within the same document still retains a validated checkpoint. Physical edits still use the exact physical key. Accepted Apply/cosmetic changes do not unnecessarily invalidate search candidates for otherwise identical authored input.

Root confirmed this gap and assigned a separate bounded ownership prerequisite to the implementation owner while this contract was being prepared. That owner may use an explicit document-reset/adoption API instead of the illustrative getter/entry scheme above. The invariant, not that API spelling, is required: replacement immediately retires completed and in-flight old-document results; old completion/finally/batch work cannot write state or stop a newer job; A→B→A stays retired; explicit same-document Cancel retains its valid checkpoint. Root owns its public-API RED/GREEN tests and integration. Do not implement a competing ownership change from this document.
