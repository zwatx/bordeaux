Initial covariance

The starting preset assumes the robot is placed within a standard deviation of 5 cm along each field axis and 3° in heading. It is an adjustable placement assumption, not measured robot accuracy. Increase it if the starting placement is less certain.

σx = 0.05 m       σy = 0.05 m       σheading = 3 × π / 180 rad

P₀ = [ 0.0025    0         0            ]
     [ 0         0.0025    0            ]
     [ 0         0         0.0027415568  ]

Bordeaux Initial Uncertainty Cluster.vi exposes named uncertainty and the private SI covariance9. It squares the chosen standard deviations internally and rejects nonfinite, zero/negative, underflowed, or overflowed values. A zero covariance must not silently become a perfect-confidence initial estimate. The off-diagonal initial terms default to zero; subsequent estimation retains cross-covariances.

Call once at the start of auto

Primary reset interface: Bordeaux Set Initial Pose.vi. Call it once in autonomous initialization, before Auto Play Path. Supply the pose and uncertainty constructor outputs (uncertainty default 5 cm, 5 cm, 3°), plus Inputs Valid = Pose.Valid AND Uncertainty.Valid. Invalid builder outputs are sanitized, so preserve their validity flags. The VI validates the complete request, submits it atomically, and waits for acknowledgment with a finite timeout. Not Before FPGA s defaults to 0, meaning the next eligible owner invocation; this does not prove the sample was acquired after submission. For that stronger guarantee supply a timestamp in the sensor clock’s verified seconds/epoch. The helper does not guess the installed FPGA clock conversion. A separate wrap-aware millisecond timer controls waiting; private acceptance time is explicitly 0/unused. No user-managed request ID, matrix, rising-edge detector, or estimator memory wiring.

The current setter design returns Applied, numeric Status, TimedOut, the request token for unresolved recovery, and ReleaseValid. Status codes are documented in the delivery guide; an NI error-cluster interface remains a future interface refinement. Its bounded mailbox accepts one outstanding request; a busy call returns a clear error without overwriting it. Its internal polling loop waits on that specific ID with a finite timeout and exact-token cancellation, and reports a status on failure. Wire the public VI's results into the auto-start condition so playback cannot start after a rejected, timed-out, or unapplied reset. Waiting occurs only in the auto initialization caller, never in the localization owner loop.

The initial robot pose can come from a configured starting-pose cluster or the selected path's first robot pose; do not use travel direction as robot heading. Do not call the setter every timed-loop iteration. A dashboard button may call the same setter, but button-edge behavior is not the primary interface.

If a shared-variable route is added, publish one request cluster including a changing request ID, target pose, uncertainty, and request timestamp. Merely assigning X/Y/heading is insufficient: resetting to the same numeric pose twice must still create two distinct requests. Prefer the setter VI so the atomic mailbox, identifiers, validation, and acknowledgment remain centralized.

Reset behavior inside the owner

  1. A single mailbox coordinator allocates IDs above both the last issued ID and the owner's last applied ID. Initialize/synchronize it against the current owner before accepting requests. IDs stay below 2,000,000,000 and never wrap. Multiple callers serialize through this coordinator.
  2. Accept and retain each new request ID once inside the mailbox, including its pose, uncertainty, and not-before time. Detect changes by ID, not by a shared boolean edge, so consecutive calls cannot merge into one reset.
  3. Claim the request for each owner attempt; complete it with the actual returned applied ID. An ineligible sample returns it to Pending. Cancellation can then prevent any later claim. Later edits to the caller's pose control must not modify an accepted request.
  4. The owner seeds pose and covariance, captures the current cumulative encoder/gyro baseline, clears old history, increments generation, and updates its internal gyro-to-field offset.
  5. Acknowledge using Owner State Out's applied request ID and the reset-applied diagnostic. Clear outward Pending in the same successful update. An ordinary successful odometry update is not an acknowledgment.
  6. Never silently queue, overwrite, or drop an outstanding request. If auto initialization times out or is cancelled, keep playback inhibited and report the request's status. Any cancellation of a still-pending request must be serialized through the mailbox so the caller can distinguish cancelled from already-applied.
  7. An invalid new pose, uncertainty, or request timestamp is rejected without replacing the active request or blocking ordinary odometry. Request validity is separate from sensor validity.

The old local boolean-edge reset draft is superseded. The call-based mailbox, owner bridge and setter have source tests for consecutive calls, ownership, and cancellation races. Native construction and saved-file error-list checks have also passed for this increment; execution is still prohibited.

This reset changes the estimator. It does not write the physical IMU, zero drive encoders, command motors, or move the robot. Route the shared aligned gyro heading through the legacy drive convention exactly once; do not feed vision-corrected heading back into the raw gyro. The drive command continues to own field-centric rotation.
