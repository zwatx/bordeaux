Original audit

The editor is visually steadier, but error recovery and delivery capability still undermine trust. Fix project-state integrity first, then make every visible action describe what it can actually do.

September 16, 2026 · Release baseline d338158a / 0.2.0-beta.10 · Read-only audit of the current working build, with pre-existing robot-integration changes distinguished below. No product files were changed.

Verdict: not ready for an unrestricted production sign-off. Nine evidenced findings: one P1, seven P2 and one P3. The recent sidebar, toolbar, focus-return and routine-branch layout fixes hold in the inspected workflows. The remaining priority is reliable behavior, not another visual redesign.

What the app should accomplish

A robot programmer should be able to choose a project, define the robot, author a path, inspect motion and commands, optionally compare an optimized route, compose routines, save reproducible files, and deliver exactly the selected supported output. Each stage should make the current project, selected trajectory, unsaved changes, and delivery capability understandable.

The path-authoring model largely meets that intent: normal planning works without optimization, candidate application is explicit, and playback/save/reload timing agrees in tested flows. The largest product gap is routine delivery: the app can compose and save routine control flow, but its active SFTP route delivers path files only. The enabled Push routine action implies an end-to-end capability the current route does not provide.

P1 · F1 — Keep the active save destination unchanged when opening a managed file fails

Opening a malformed .path inside project B activates B before parsing fails. The renderer retains project A, while the main process points at B and clears its dirty flag. Subsequent saves can be misdirected; distinct item IDs can allow A to replace B's recovery/project snapshot. Ownership checks may block writes when a corrupt mirror's ID collides, so overwrite is conditional.

Evidence: Source plus extracted-handler filesystem probe; independently reviewed.

Correction: Load and validate the entire selection before committing target, recent-project, linked-project and dirty-state changes. Every failed Open must retain A and its original save destination.

Acceptance: Open A, attempt malformed managed .path in B, assert error while renderer, destination, dirty state and robot link remain A; save and verify B is unchanged.

Product and design recommendations

Make Project the complete home for project actions

The in-window Project menu contains Open, Save and Save as, while New and Open Recent live only in the native menu. This is a discoverability gap, not an absent capability. Add New and recent projects to the same menu, using the same shared commands. First define New precisely: the current native command chooses/opens a folder, so it must not imply that an existing folder will be cleared. Keep source autosave, explicit BDX generation and robot push distinct.

Use quiet progress consistently without hiding job identity

Opening Optimize no longer launches a job or flashes loading prose, and its sidebar shares the inspector width. Connection and file-preparation screens still use Loading/Preparing/Connecting text. As a follow-up to the owner's preference, retain context and use a stable progress affordance with an accessible status, a named operation and cancellation where useful. Do not remove the distinction between transfer completion and robot execution.

Keep the current visual system and strengthen state consistency

At 1440×900 and 1100×720, inspected toolbar/menu controls, branch labels, custom-footprint inputs and long file destinations are readable. The editor retains a useful field area with the inspector open. Stronger priorities than restyling are consistent numeric draft validation, truthful disabled actions, and retries tied to the operation that failed. Use the existing controls rather than another menu, number-field or dialog variant.

Limits and remaining proof

This is an app-wide audit with representative states, not proof of every possible combination. No real robot, NI installation, live SSH network or robot runtime was exercised. There was no native Windows/Linux run, screen-reader session, fresh frame-rate benchmark, exhaustive large-project stress test or actual updater installation. Some interactions use the established harness's programmatic controls; important menu/focus and additional repro probes use native pointer/keyboard input. The malformed-open probe extracts the real handler and uses filesystem helpers with stubbed activation, rather than claiming a native-dialog end-to-end run.

The current source is architected to keep planner work off the UI thread, but that is not a measured performance result. Existing mocked success must not be treated as proof of robot execution. File readback confirms stored bytes; activation/runtime acknowledgment requires its own supported protocol and evidence.

Recommended implementation order

  1. Make project activation atomic and protect reload from draft loss.
  2. Correct operation-specific recovery and make failed paths repairable; align routine delivery actions with capabilities.
  3. Unify Wait validation and display running optimizer ownership.
  4. Add update recovery and correct shortcut help.
  5. Complete Project menu discoverability and quiet-progress consistency; separately land and verify the already-tracked robot destination changes.
