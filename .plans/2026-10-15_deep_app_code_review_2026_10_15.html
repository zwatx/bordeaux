F1 · P1 — Bind every pending Open to its original window and document

Location: src/electron/main.ts:773–779, with the unguarded caller at 794–796; consequence at src/renderer/app/App.jsx:831–840.

Window W1 begins opening A and stalls during filesystem work. W1 crashes and the supported Reopen action creates W2. W2 opens B. The old Open finishes and calls activateProjectSelection without an original window/context guard, replacing the global source target and document session with A. Its IPC response belongs to the old renderer, so W2 still displays B. On the next edit, the renderer fetches main's fresh context and submits B under A's new session. All subsequent source lease checks therefore pass.

Evidence: persistence-probes/stale-open-data-loss.cjs extracts the actual main functions and uses the real loader, persistence, recovery, atomic writer, and temporary folders. It reports source: saved; A changes to “B edit made in replacement window,” while B remains “B original.” The root reviewer repeated this successfully. Native window replacement and old-response delivery are modeled; the crash/Reopen caller was traced in source. This is not a claim that a real Electron crash was induced.

Cause: assertCurrent is optional at the exact state-changing boundary. Capturing the generation after activation protects later completion, but cannot stop the stale activation itself. A pre-call guard alone also leaves the awaits inside activation unprotected.

Focused fix: capture original window/document/transition ownership before the first dialog or read, require it through every asynchronous admission, and assert synchronously immediately before changing the active target. Retiring a renderer must invalidate pending opens. Add the full old-Open → new-window B → old completion → edit regression and verify both target and file contents.

F2 · P2 — Preserve the physical identity of an opened source folder

Location: src/electron/projectSourcePersistence.ts:164–176; integration at projectPersistence.ts:287–300.

After opening A in Active, move that folder to an archive outside Bordeaux and put a different valid Bordeaux project B at Active. The editor still holds A. Its next autosave obtains the replacement directory's current identity and treats that new identity as write authority. It reads B's valid managed-file journal and overwrites B with A, without comparing the directory to the identity admitted when A opened.

Evidence: persistence-probes/replaced-folder.cjs calls the real implementations, admits A's original recovery identity, then swaps two real temporary directories. It proves the physical object key changed; the next checkpoint nevertheless returns saved and changes “Irreplaceable B” to “Later A edit.” The root rerun confirms it. This trigger requires external directory replacement; it is distinct from merging arbitrary external edits to a file.

Focused fix: retain source identity for the active document separately from recovery provenance. Ordinary autosaves must compare against that identity. On replacement, preserve the new folder and surface a source-changed outcome. Explicit reopen or Save As can admit a new destination; legitimate path aliases should remain supported. The regression must verify B's original content survives.

F3 · P2 — Keep explicit BDX Export consistent with managed file ownership

Location: src/electron/main.ts:1094–1095; ownership enforcement at src/electron/projectFiles.ts:355–364,485–487.

Save a project to generate Paths/NewPath.bdx, edit the path, then use Export BDX to replace that same file and approve Replace. The explicit export writes new bytes directly, leaving the workspace's generated-file hash unchanged. The next ordinary Save rejects Bordeaux's new bytes as an external modification: “Paths/NewPath.bdx is unrelated or changed outside Bordeaux. Preserve or rename it before saving again.” The source save can succeed while BDX output remains blocked.

Evidence: persistence-probes/selected-export-ownership.cjs executes the extracted actual export handler with the real filesystem, source autosave, atomic writer, and managed-output writer. Only compiler bytes and native dialogs are controlled. Export succeeds; a subsequent managed write of the same bytes fails. Independently repeated by the root reviewer.

Focused fix: route managed destinations through a single-output lease and ownership update, or reject that destination with a clear path to Save or an external export location. Preserve sibling outputs: the existing full-set writer must not be called with only one selected file if doing so deletes other managed files. Retain protection for genuinely external changes.

F4 · P2 — Guard endpoint actions for valid unfinished paths

Locations: src/renderer/app/App.jsx:1648–1651,1674–1675; src/renderer/lib/pathEditing.ts:74–76; callers at EditorLibrary.jsx:281 and ContextInspector.jsx:467–475.

The editor deliberately creates and saves zero-waypoint paths. Several visible actions still assume endpoints exist. Append reads the absent last waypoint's heading; linking reads an absent endpoint on either path; initial-facing editing assigns onto waypoint 0; reverse reads the absent last waypoint's jiggle. The library offers Append without an endpoint guard, link options include unfinished paths, and the More inspector exposes facing and reverse for the empty path.

Evidence: renderer-probes/unfinished-paths.cjs extracts the production App owners and imports actual path helpers. Five assertions reproduce TypeError for append, both link directions, initial facing, and reverse. Callers were inspected to establish availability. This is production-function and caller verification, not a native mouse-driven UI test; the finding is failed actions, not an unproven claim that every exception crashes the entire application.

Focused fix: make empty-path support explicit in action owners and UI prerequisites. Hide or disable endpoint-dependent actions with useful explanations, and make the owners safe against stale selection anyway. Add zero-, one-, and two-waypoint workflow tests. Do not make valid unfinished projects unsavable to avoid these actions.

F5 · P2 — Use one wait-duration contract for generation and acceptance

Location: src/shared/planners/acceptedTrajectory.ts:44; producer at stationaryActions.ts:95–101,248,309–310; adoption at src/renderer/app/App.jsx:1934–1945.

A valid slow curved path with a terminal wait of 0.11 seconds optimizes successfully. The sampler uses a 50 ms interval and rounds the wait to 0.15 seconds. Accepted-result validation permits only 21 ms difference, so it rejects the 40 ms discrepancy. Apply constructs and stores the artifact directly, without resolving this mismatch. Subsequent artifact selection and export reject the applied optimization.

Evidence: the real optimize worker returns feasible, no fallback, zero constraint violations, and a 0.847165-second improvement (14.361595 → 13.514430 seconds). The App-shaped artifact passes source and shape validation, but buildBdxExport throws “The applied optimization is invalid.” planning-probes/probe.test.ts asserts the result, with detailed output in WAIT.json. The fixture uses a default demo robot, endpoints (7,1) and (9,1), handles (7,2)/(9,2), maximum speed 0.2 m/s, and final stop/wait 0.11. The numerical input retains the typed 0.11.

Focused fix: keep exact requested wait duration using a shorter final interval, or make the accepted validator honor the producer's actual permitted quantization. Add a real candidate → App-shaped application → selection/export test with a non-tick-aligned wait. Repeating Optimize unchanged is not a remedy; Use normal is a temporary escape. Immediate in-memory preview behavior is separate from the demonstrated reread/export failure.

F6 · P2 — Align exact integer validation with binary serialization

Location: src/shared/export/robotBinary.ts:49–51; accepted input at src/shared/robotCommands.ts:23–33 and src/renderer/components/ContextInspector.jsx:188–218.

The editor and shared schema accept exact I64 strings such as +42, 0042, and -0042, preserving the original trimmed spelling. The binary encoder requires a narrower canonical spelling and throws “NI I64 requires an exact integer.” The nonnegative variants have the same mismatch for U64. These are valid in-range integer values, not floating-point precision or overflow problems.

Evidence: planning-probes/integers.test.ts uses the existing binary-writer fixture. All three failing values pass field and project invocation validation, then fail full binary export; canonical 42 succeeds with identical bindings. INTEGERS.json records each outcome. The fixture is synthetic NI type evidence, not a connection to a real team's VI.

Focused fix: normalize validated strings with BigInt or use the same exact grammar at validation and encoding. Preserve width, range, and exactness checks; never normalize through Number. Test alternate accepted spellings through full export, including signed/unsigned boundaries.

F7 · P2 — Validate MCP editor snapshots as editable source

Location: src/electron/agentSession.ts:314–318, particularly validateProject at line 316.

The renderer publishes the whole editable project. A zero- or one-waypoint sibling is valid authoring state, even with a complete path selected. The MCP service uses strict execution validation, rejects the new snapshot, and retains its last valid one. Session inspection then reports the old name, revision, and path list; analyses can run against old geometry. A newly enabled session with unfinished source fails inspection with “wait for the editor to finish loading.”

Evidence: boundary-probes/incomplete-agent-snapshot.test.ts tests the real service and validators for both zero and one waypoint. It asserts valid source, rejected publication, old returned session data, and failure of a fresh session. The renderer's revision guards stop stale proposals from silently applying, so the demonstrated impact is stale information and blocked functionality, not unauthorized project mutation or robot execution.

Focused fix: use editable-source validation for snapshot synchronization and inspection; keep strict selected-path checks for planning/export. Do not describe a retained old snapshot as current if a genuinely invalid newer one must be rejected. Cover a complete active path with an unfinished sibling and an unfinished selected path separately.

Maintainability and architecture

Useful foundations: explicit optimization application, immutable transfer preparation, source/recovery separation, ownership journals, constrained SFTP, and worker cancellation provide concrete protection. Production transfer checks selected immutable bytes, known host fingerprints, and temporary/final readbacks. Late preparations are discarded; navigation does not silently change an in-flight upload's selected contents. These are source-backed observations supported by focused tests, not a certification of live robot operation.

Highest-value structural change: make state-changing boundary contracts hard to omit. F1 and F2 show that fresh per-operation validation cannot replace retained ownership of the document and destination. Project activation should require a transition owner and source writes should require an admitted destination identity. Avoid a broad rewrite; deepen those existing APIs so callers cannot accidentally omit the invariant.

Consolidate validity rules: F4/F7 show editable source differs from executable paths, while F5/F6 show independently implemented producer/consumer rules drifting. Share capability predicates and value normalization where the same contract crosses UI, storage, worker, and binary boundaries. Keep execution-specific checks at the selected execution boundary rather than rejecting unrelated unfinished source.

Target integration tests: many useful unit tests exist, but the reproduced failures require composing main activation with renderer autosave, explicit export with managed ownership, and optimizer candidates with subsequent selection/export. Add regression tests at these public boundaries. The 2,774-line snapshot App still owns many lifecycle, geometry, history, and native bridge decisions; extract cohesive owners when fixing these flows rather than reorganizing unrelated UI.

Typecheck limitation: tsconfig.renderer.json has allowJs: true and checkJs: false. Passing typecheck does not type-check all JSX action bodies, including the absent-endpoint cases. Focused typing of action contracts and empty-state tests would add more value than claiming the current green check covers all renderer behavior.
